# 코드 리뷰 — 파일별 상세 (데이터 파이프라인)

> 컴패니언 문서: 아키텍처/플로우는 [`코드리뷰_모니터링_시스템.md`](./코드리뷰_모니터링_시스템.md), 여기서는 **파일별 중요 코드·흐름·왜 필요한지**.
> 파이프라인 순서: **로봇(ROS2) → 수집 → 저장경계(펌프 스위치) → 로컬(SQLite+Flask UI) / 클라우드(Supabase+Vercel)**
> 불변식: **관측 전용** — 미션 생성·로봇 제어 없음. 저장 백엔드는 `FMS_BACKEND` 한 변수로 전환.

---

## A. 입력·수집 계층 (ROS2 → 서비스) — 로컬·클라우드 공통

모든 외부 입력이 `RosIngestNode` 한 노드에서 정규화되고, 이벤트는 typed/JSON 두 경로가 `event_service.record_event` 하나로 수렴한다.

### `main.py` (88줄)
- **목적**: 엔트리포인트. store 초기화 → rclpy 초기화 → ingest 노드 생성 → (백엔드 분기) Flask 기동 여부 → `rclpy.spin`.
- **중요 코드**: `start()`(L35–53) — `store.init()` → `rclpy.init()` → `RosIngestNode(registry)`. **백엔드 분기(L44–53)**: `config.BACKEND=="supabase"`면 Flask 미기동("ingest → Supabase, no local API"), 아니면 `api.run_api`를 daemon 스레드로 띄움. `run_forever()`(L70–80) SIGINT/SIGTERM→`rclpy.shutdown`, `spin`. `stop()`(L55–68) 멱등 정리.
- **흐름**: 시작 → 초기화 → ingest 생성 → supabase면 펌프만 / sqlite면 +Flask → spin → 시그널 시 정리.
- **왜 필요**: 한 프로세스를 "로컬 SQLite+API" 또는 "Supabase 쓰기 펌프" 두 역할로 부팅하는 라이프사이클 묶음.

### `ros_ingest.py` (122줄)
- **목적**: ROS2 구독 정의 + 콜백에서 파싱→서비스 라우팅하는 단일 수집 노드.
- **중요 코드**:
  - **노드 이름 BACKEND 접미사(L25)**: `f"monitor_server_ros_ingest_{config.BACKEND}"` — sqlite·supabase 동시 기동 시 같은 노드 이름이면 discovery/구독 충돌로 한쪽이 메시지를 못 받음(2026-06-10 수정).
  - **구독 토픽(L29–69)**: 로봇별 `/{id}/robot_state`(RobotState)→`_on_robot_state`, `/{id}/vision/alert`(Event)→`_on_event`, `/{id}/detection/info`(String)→`_on_detection_info` + 전역 `/information`(String)→`_on_information`.
  - **콜백**: `_on_event`(L74–88) typed Event를 dict화(class→class_name fallback, location.x/y + 최상위 floor) → record_event. `_on_detection_info`(L90–93) JSON 파싱→record_event. `_on_information`→언랩→usage_service.
  - **파서**: `_loads_json_msg`(L102–111) JSON+dict 검증, `_unwrap_rosbridge_payload`(L114–122) rosbridge 봉투/이중직렬화(`{"data": "..."}` 한번 더 loads) 처리.
- **흐름**: 토픽 수신 → (typed면 getattr / String이면 JSON 파싱·언랩) → record_event/record_information/registry. 파싱 실패는 warning 후 흡수.
- **왜 필요**: 외부 ROS 도메인과 내부 store 사이 **유일한 입력 경계**. 정형·비정형·rosbridge 메시지를 한 곳에서 정규화.

### `robot_registry.py` (105줄)
- **목적**: RobotState를 최신상태(`latest_robot_status`) upsert + 변화 시 이력(`robot_status_log`) append.
- **중요 코드**: `update_from_ros_state`(L89–105) typed→dict(빈문자열 `or None`). `update_from_status`(L20–87): robot_id 없으면 무시, state가 `ROBOT_STATES` 밖이면 warning만(기록 진행), **floor는 메시지가 아니라 `config.ROBOTS[id]["floor"]`로 보강(L36)**, `store.get_prev_status`로 직전 비교 → 항상 `upsert_robot_status`, `prev_state/prev_task_status` 변화 시에만 `append_status_log`.
- **흐름**: 수신 → 정규화 → 항상 최신 갱신 → 변화 시에만 이력+전이 로그.
- **왜 필요**: 고빈도 상태를 "현재값 1행"과 "전이 이력"으로 분리 → 실시간 표시 + 변화 추적, 로그 폭주 방지.

### `event_service.py` (45줄)
- **목적**: 디텍터 이벤트 정규화·검증 → `store.insert_event`.
- **중요 코드**: `record_event`(L18–45) — **EVENT_TYPE_ALIASES 치환(L20)** (`INJURED_PERSON`→`EMERGENCY_PATIENT`), 필수값(event_type/robot_id) 검증, enum 밖이면 warning만, location.x/y/floor·timestamp 정규화 → insert_event(msg_id/event_type/event_class(=payload `class`)/robot_id/confidence/x/y/floor/snapshot_ref/at), 알람성 warning 로그.
- **흐름**: payload → 별칭 → 검증 → 정규화 → insert_event. typed/JSON 두 경로가 여기로 수렴.
- **왜 필요**: 비전 알람의 단일 저장 경로 + enum 정규화.

### `usage_service.py` (38줄)
- **목적**: 키오스크 UI 상호작용(IF-01) → `store.insert_usage`.
- **중요 코드**: `record_information`(L17–38) — request_type ∈ {INTERACTING,ESCORT,CANCEL} 검증, **CANCEL은 저장 안 함(L22–23)**, customer.language/profile 추출(중첩/평탄 fallback), `escort_used=1 if ESCORT`, insert_usage.
- **흐름**: 언랩 payload → 검증 → CANCEL 스킵 → 필드 추출 → insert_usage.
- **왜 필요**: 이용 통계(언어·프로필·에스코트 여부) 저장 경로.

### `messages.py` (58줄)
- **목적**: 테스트/데모용 IF-02·IF-05 메시지 dict 빌더.
- **중요 코드**: `_envelope`(msg_id/version/timestamp), `if02`(RobotState형), `if05`(L41–58) — **`class` 키(인자 `event_class`)** 가 event_service의 `payload.get("class")`와 계약 일치.
- **왜 필요**: 수집 경로 테스트에서 정의서와 동일 키 구조 메시지 생성. (← `~/Downloads/publish_/*.py` 가 이걸 import)

### `states.py` (39줄)
- **목적**: 상태·이벤트 enum + 별칭(검증 단일 출처).
- **중요 코드**: `ROBOT_STATES`(10종), `EVENT_TYPES`(FIRE/SUSPICIOUS_PERSON/EMERGENCY_PATIENT/INJURED_PERSON/LOST_ITEM), `EVENT_TYPE_ALIASES`(INJURED→EMERGENCY).
- **왜 필요**: registry/event_service 검증·치환의 데이터 정의.

### `poi.py` (48줄)
- **목적**: POI 좌표/층 조회 헬퍼(yaml 캐시).
- **⚠ 주의**: **현재 수집 파이프라인 어느 파일도 import 안 함**(미사용 스텁). 관측 전용 설계와 일관(명령용 좌표 변환이 불필요).

## B. 저장 경계 (펌프 스위치)

### `config.py` (68줄)
- **목적**: 환경변수 기반 설정 단일 출처(ROS 토픽/QoS, 백엔드 선택, Supabase 접속, Flask/관리자, POI).
- **중요 코드**: `ROBOTS`/`ROBOT_IDS`(robot2=1층/robot4=2층, 정보용), ROS 토픽 헬퍼(`ros_robot_state_topic`/`ros_event_topic`/`ros_detection_topic`/`ROS_INFORMATION_TOPIC`), QoS(depth 10), `STATUS_TIMEOUT`(10s, freshness용), **`BACKEND=getenv("FMS_BACKEND","sqlite").lower()`(L46)**, `SUPABASE_URL/SERVICE_KEY/TIMEOUT`, Flask/ADMIN, `load_poi_table()`.
- **흐름**: import 시 env→상수 고정 → 모든 모듈이 `config.X` 참조. `BACKEND`가 store 분기를, 토픽 헬퍼가 구독 대상을 결정.
- **왜 필요**: 코드 수정 없이 `FMS_BACKEND` 한 변수로 로컬↔클라우드 전환하는 스위치 + 단일 진실 소스.

### `store.py` (244줄) — **리뷰 핵심**
- **목적**: 저장 백엔드 추상화. `FMS_BACKEND`에 따라 SQLite 또는 Supabase PostgREST 펌프로 동일 인터페이스 디스패치.
- **중요 코드**:
  - `SqliteStore`(L37–100): `import db` 위임. `upsert_robot_status`(ON CONFLICT), `append_status_log`, `insert_event`, `insert_usage`, `get_prev_status`. **list/resolve/stats 메서드 없음.**
  - `SupabaseStore`(L106–199): `rest={URL}/rest/v1`. `init`(URL/KEY 없으면 RuntimeError). **`_request`(L123–144)** apikey+Bearer(**service_role**), Prefer, urlopen(timeout), HTTPError/URLError 로깅 후 **raise**. `upsert_robot_status`(POST `?on_conflict=robot_id` + merge-duplicates), insert/append(POST return=minimal), **`list_events`/`resolve_event`(GET→없음/이미해결/PATCH 3분기)/`event_stats`** 자체 제공.
  - `get_backend()`(L208–215): `config.BACKEND` 기준 싱글턴. 모듈 레벨 위임 함수(L218–244).
- **흐름**: 백엔드 선택(1회 캐시) → 쓰기 rec → sqlite=db.execute / supabase=`_request(POST)`. 상태변화=get_prev_status. resolve(supabase 전용)=3분기. 오류=로깅 후 raise.
- **왜 필요**: "로컬 sqlite ↔ supabase 펌프" 전환 경계. ROS 콜백은 `store.insert_event` 등만 호출, 목적지는 `config.BACKEND`가 결정.
- **⚠ 리뷰 포인트**: `list_events`/`resolve_event`/`event_stats`는 **SupabaseStore에만** 존재 → sqlite 백엔드에서 호출하면 `AttributeError`. 또 이 3개는 모듈 레벨 위임 함수로 노출 안 됨(api.py가 `SupabaseStore`를 직접 인스턴스화해 사용 → 아래 `_sb_events`).

### `db.py` (159줄) — **로컬 DB(SQLite)**
- **목적**: 로컬 SQLite 저장소(스키마/WAL/스레드 안전 헬퍼).
- **중요 코드**: 전역 `_conn`+`_lock`(단일연결 직렬화). **SCHEMA 5테이블**: `latest_robot_status`(robot_id PK 최신 1행), `robot_status_log`(이력+prev_state), `events`(탐지+resolve 필드), `ui_usage_log`, `monitor_counters`. `init_db`(WAL+synchronous=NORMAL+foreign_keys, SCHEMA→`_migrate`→INDEXES). `_migrate`(events에 msg_id/event_class/resolved* 누락 시 ALTER — 구버전 호환). `execute`(lock+commit 쓰기)/`query_all`/`query_one`(lock+fetch 읽기).
- **흐름**: 최초 접근 시 init(WAL/스키마/마이그레이션) → 쓰기 execute / 읽기 query.
- **왜 필요**: 로컬 경로 실저장 엔진. `SqliteStore`가 전부 위임. WAL+lock으로 ROS 다중 콜백 스레드 동시 쓰기 안전화.

## C. 로컬 경로 — 관제 UI (localhost:5000)

### `api.py` (399줄)
- **목적**: 읽기 전용 Flask API + 로그인 가드 + 정적 페이지/지도/영상 메타 서빙.
- **중요 코드**:
  - **`_sb_events` 초기화(L22–33)**: `config.SUPABASE_URL` 있으면 `SupabaseStore()` 생성·init(주석: "이벤트는 Supabase 단일 소스, resolve가 외부 보안팀 뷰와 동기화. 로봇상태/사용량은 로컬 유지"), 예외 시 None(SQLite 폴백).
  - 로그인 가드 `require_login`(L113–122): /login·/logout 통과, 세션 user 없으면 `/api/*`·`/maps/*`=401, 그 외 `/login` 리다이렉트.
  - **`/api/events`(L199–209)**: `_sb_events`면 `list_events`, 아니면 SQLite.
  - **`/api/events/<id>/resolve`(L211–225, POST)**: `_sb_events`면 `resolve_event`, 아니면 SQLite UPDATE.
  - `/api/robots`(L195) 항상 SQLite(`_robot_snapshots` + ROBOT_IDS 병합, age_s/online). `/api/stats`(L266) 이벤트 통계만 `_sb_events` 분기, 사용량은 항상 SQLite. `/api/robot_log`·`/api/search`·`/api/system` SQLite. `/api/floor_data`(POST, 유일 쓰기계열), `/api/video_sources`, `/`·`/viz`·`/maps/<f>`.
- **흐름**: 요청 → 가드(세션) → 핸들러 → 이벤트(조회/통계/resolve)는 `_sb_events` 있으면 Supabase, 아니면 SQLite → jsonify.
- **왜 필요**: 로컬 LAN 관제 백엔드. **이벤트만 Supabase 단일소스 가능, 나머지는 로컬 SQLite** — 이 비대칭이 핵심.
- **⚠ 리뷰 포인트**: `/api/system`의 events count·`/api/search`의 events는 `_sb_events` 분기가 **없어** supabase 모드에서도 SQLite를 읽음 → `/api/events`·`/api/stats`와 수치 불일치 가능.

### `web/dashboard.html`
- **목적**: 단일 HTML/JS SPA 관제(8탭, 2초 폴링).
- **중요 코드**: `load()`(L382–386) `Promise.all`로 `/api/robots`,`/api/events?limit=50`,`/api/events?active=1&limit=30`,`/api/stats`,`/api/system`,`/api/robot_log` 동시 폴링(`setInterval 2000`). `resolveEvent(id)`(L365–368) → `POST /api/events/<id>/resolve` → `load()` 재호출(개요 알람 카드 + 이벤트 탭 "조치완료" 버튼). 401이면 `/login` 이동. 영상 탭은 폴링 밖 lazy build + 로봇 P2P.
- **왜 필요**: 관제사 프런트엔드. **소스(SQLite/Supabase)를 모르고 `/api/events`·resolve만 호출** → 소스 전환은 서버 `_sb_events`에 위임.

### `web/login.html`
- **목적**: `POST /login` 폼(정적, 검증은 서버 `check_password_hash`). `?e=1`이면 에러 표시.
- **왜 필요**: UI 진입 게이트(세션 쿠키 인증 접점).

### `web/video_sources.json`
- **목적**: WebRTC 영상 소스 메타(로봇별 `signal_url`만, 미디어는 P2P).
- **중요 코드**: robot2=`:8081/offer`, robot4=`:8082/offer`. `/api/video_sources`가 그대로 전달.
- **왜 필요**: 영상 탭 설정 소스(서버 DB 무관, 미디어는 FMS 우회 직결).

## D. 클라우드 경로 — Supabase + Vercel

### `supabase/01_schema.sql` (135줄) — **Supabase DB**
- **목적**: 로컬 SQLite 스키마를 Postgres로 포팅 + Realtime + RLS.
- **중요 코드**: 5테이블(`latest_robot_status` PK robot_id / `robot_status_log` identity / `events`(resolved int + resolved_at/by) / `ui_usage_log` / `monitor_counters`). SQLite→PG 변환 주석(timestamptz, identity, double precision, **resolved/escort_used는 JS 호환 위해 0/1 정수 유지**). 인덱스. **Realtime 퍼블리케이션(L90–101)** latest/events/status_log. **RLS 전 테이블 활성(L111–115)**, 정책(L117–135): 모든 테이블 `read_all`=authenticated select / events에만 `resolve_events`=authenticated update.
- **왜 필요**: 클라우드 저장 + 변경 푸시(Realtime) + 접근 통제. **anon 단독 읽기 불가, 로그인(authenticated)만 읽기, 쓰기는 service_role.**

### `supabase/02_functions.sql` (271줄)
- **목적**: 무거운 집계를 RPC로(대시보드가 `supabase.rpc()` 호출) + `robots` 메타 테이블.
- **중요 코드(RPC)**: `get_robots`(robots⟕latest, age_s/online) / `get_stats`(이벤트·언어·프로필·escort·vulnerable) / `search_monitor`(ilike) / `get_system`(online·테이블 count) / **`resolve_event(event_id)`(L243)** — `who=auth.jwt()->>'email'`, 이미해결이면 already, 아니면 `update events set resolved=1, resolved_at=now(), resolved_by=who`. 전부 `security definer set search_path=public`. **Grants: 5함수 모두 authenticated 전용(anon 없음).**
- **왜 필요**: Flask `/api/*` 집계를 클라우드에서 동일 제공. resolve를 RPC 한 경로로 최소화.
- **⚠ 리뷰 포인트**: 헤더 주석은 "anon+authenticated grant"라 하나 **실제 grant는 authenticated 전용** → 주석/코드 불일치.

### `supabase/03_grants.sql` (21줄)
- **목적**: 역할별 테이블 GRANT(RLS만으로 부족한 부분 보강).
- **중요 코드**: `grant usage on schema public to authenticated, service_role`(**anon 없음**). service_role=전 테이블 DML(ingest·RLS 우회), authenticated=**select만**. `alter default privileges`로 향후 테이블 상속.
- **왜 필요**: anon은 schema usage조차 없어 직접 접근 완전 차단. 운영자 읽기전용, resolve는 RPC로만.

### `web-vercel/index.html` — **Vercel UI**
- **목적**: supabase-js로 RPC/테이블/Realtime 쓰는 단일 파일 정적 대시보드(로그인 게이트).
- **중요 코드**: `createClient(url, anonKey)`(L236). **읽기 load()(L405–416)**: `rpc('get_robots'|'get_stats'|'get_system')` + `from('events').select` (이력/active) + `from('robot_status_log').select`. 검색=`rpc('search_monitor')`. **resolve(쓰기)=`rpc('resolve_event',{event_id})`(L387–391)** → load() 재호출(PATCH 아님, RPC). **Realtime(L512–515)**: `channel('monitor')` postgres_changes on latest/events → load() + 5s 폴링. 로그인=`signInWithPassword`. 영상=video_sources.json LAN P2P(Supabase 무관).
- **왜 필요**: 외부 공개 관제 UI. anon 키로 client 생성하되 **로그인 후 JWT(authenticated)** 로만 RLS 통과.

### `web-vercel/supabase-config.js`
- **목적**: 브라우저 노출용 공개 URL/anon키.
- **중요 코드**: `window.SUPABASE_CONFIG={url, anonKey, statusTimeout}`. 주석: 둘 다 공개 설계값, anon키 단독은 RLS로 읽기 불가.
- **⚠ 리뷰 포인트**: **실제 프로젝트 URL + publishable(anon) 키가 리포에 커밋됨**. 설계상 공개값이나, 리뷰 시 (a) 진짜 publishable 키인지 (b) RLS가 전 테이블 실제 켜졌는지 재확인.

### `web-vercel/vercel.json`
- **목적**: Vercel 정적 배포 설정. `cleanUrls:true`, `/supabase-config.js`에 `Cache-Control: no-store`(키 교체 시 캐시 옛값 방지).

## E. 코드 리뷰 시 짚을 핵심 포인트

### 설계 강점 (설명 포인트)
1. **단일 스위치(`FMS_BACKEND`)** 로 로컬/클라우드 저장 전환 — 호출측(ingest)은 백엔드 무지.
2. **관측 전용 불변식** — 미션/제어 없음, enum 밖 값은 warning만 남기고 보존(누락 방지).
3. **최신값/이력 분리** + ROS 다중 스레드 WAL+lock 직렬화.
4. **2키 보안 모델** — service_role(LAN 펌프, RLS 우회 쓰기) ↔ anon(브라우저, 로그인 후 RLS 통과 읽기). resolve는 authenticated 전용 RPC 한 경로.
5. **이벤트 single-source(Option A)** — Supabase 설정 시 로컬·Vercel 두 대시보드가 같은 events 행을 읽고/resolve → 조치 양방향 동기화.

### ⚠ 논의/개선 후보 (실제 발견)
1. **store.py 비대칭**: `list_events`/`resolve_event`/`event_stats`가 SupabaseStore에만 → sqlite 백엔드 직접 호출 시 `AttributeError`(현재는 api.py가 `_sb_events`로 우회).
2. **api.py 소스 분기 누락**: `/api/system` events count·`/api/search` events는 `_sb_events` 분기 없이 항상 SQLite → supabase 모드에서 `/api/events`·`/api/stats`와 수치 불일치 가능.
3. **이벤트 split-brain 함정**: 로컬 대시보드를 `SUPABASE_URL` 없이 띄우면 sqlite 이벤트로 폴백 → Vercel과 resolve 따로 놀음. (해결: 로컬도 `.env` 로드 후 `FMS_BACKEND=sqlite`.)
4. **노드 이름 충돌**: ingest 노드 이름이 백엔드별로 갈리지 않으면 sqlite+supabase 동시 기동 시 한쪽이 메시지 누락(→ `_{BACKEND}` 접미사로 수정 완료).
5. **02_functions 주석/코드 불일치**: "anon grant" 주석 vs authenticated 전용 실제 grant.
6. **잉여 정책**: events `resolve_events` 테이블 UPDATE 정책이 GRANT 없어 무력하지만 남아있음 — 정리 대상.
7. **공개 키 커밋**: web-vercel/supabase-config.js에 실 URL+anon키 — 의도/RLS 재확인.
8. **운영 미완**: `notifySecurity`는 `alert()`만(실 통보 X), WebRTC는 STUN/TURN 없는 LAN 전용(외부 미동작).
9. **poi.py 미사용**: 수집 파이프라인에서 import 안 됨(스텁).

### 리뷰 진행 추천 순서
`config.py`(스위치 이해) → `db.py`(로컬 스키마) → `store.py`(저장 경계, 핵심) → `ros_ingest.py`+서비스(수집) → `api.py`(`_sb_events` 분기) → `supabase/*.sql`(RLS/RPC) → `web-vercel/index.html`(2키 모델·resolve RPC).
